## 一、 系统整体架构

Domain Scanner 基于 **Rust (Edition 2024)** 与 **Tokio 异步运行时** 构建，核心架构分层如下：

```
┌────────────────────────────────────────────────────────────────────────┐
│                        外部接入层 (Clients & AI)                       │
│   Web Dashboard (Vanilla JS + Tailwind)  │  AI Agents (MCP Protocol)   │
└────────────────────────────────────┬───────────────────────────────────┘
                                     │
┌────────────────────────────────────▼───────────────────────────────────┐
│                     网络服务层 (Axum & Tower)                          │
│   REST API (/api/*)  │  SSE Streams  │  MCP Streamable HTTP (/mcp)     │
└────────────────────────────────────┬───────────────────────────────────┘
                                     │
┌────────────────────────────────────▼───────────────────────────────────┐
│                     后台扫描调度引擎 (Scheduler Core)                   │
│   TaskControl (原子信号)  │  CandidateFeeder  │  Worker Pool (MPSC)     │
└────────────────────────────────────┬───────────────────────────────────┘
                                     │
┌────────────────────────────────────▼───────────────────────────────────┐
│                  多源检查流水线 (Checker Registry)                     │
│  [LocalReserved] ──> [DNSHE] ──> [DoH] ──> [RDAP] ──> [WHOIS]           │
│  (优先级排序、独立 CircuitBreaker 熔断与全局信号量控制)                │
└────────────────────────────────────┬───────────────────────────────────┘
                                     │
┌────────────────────────────────────▼───────────────────────────────────┐
│                    数据持久层 (SQLite with WAL)                        │
│   scans │ scan_payloads │ results │ scan_logs │ dictionaries │ tlds     │
└────────────────────────────────────────────────────────────────────────┘
```

## 二、 启动执行链

服务在 `src/main.rs` 中按严谨的 10 步依赖序列启动：

1. **CLI 参数解析**：基于 `clap` 解析端口 `--port` 与子命令（如 `mcp`）。
2. **初始化 SQLite**：以 WAL（Write-Ahead Logging）模式打开 `data/scans.db` 并应用建表 DDL。
3. **加载运行时配置**：从数据库中的配置表读取（若存在旧版 `config.json` 则自动迁移至数据库）。
4. **日志系统初始化**：配置按天滚动的日志文件；标准输出重定向控制台输出至 `stderr`，保障子进程 MCP 管道的安全性。
5. **播种与合并注册局映射**：初始化默认 TLD 与 WHOIS 映射表。
6. **装配 CheckerRegistry**：依序初始化各个检查器并计算优先级。
7. **构建应用上下文 `AppState`**：组装数据库池、任务控制标志（`TaskControl`）以及 SSE 分发总线（`StreamHub`）。
8. **启动恢复与计数修复**：执行 `recover_startup_tasks`，修复异常退出的瞬态状态（如 `pausing` / `cancelling`），并通过实际结果行重算已处理/发现计数。
9. **启动后台 Worker 调度协程**：监听任务唤醒通道，开始常驻轮询与执行。
10. **装配路由并侦听服务**：挂载 REST API、公开发布目录服务、MCP 端点及前端静态资源。

## 三、 多源域名检查流水线

域名注册状态判定遵循严格的**权威性优先、短路求值**原则：

```
候选域名
   │
   ▼
[LocalReservedChecker] (Priority 0)   ──> 命中 RFC 2606 等保留名？ (短路退出)
   │
   ▼
[DnsheChecker] (Priority 5)           ──> 是否属于 DNSHE 独占后缀？ (权威判定)
   │
   ▼
[DohChecker] (Priority 10)            ──> NS 记录是否存在？ (存在则判定已注册)
   │
   ▼
[RdapChecker] (Priority 20)           ──> IANA Bootstrap / 注册局 RDAP 响应？
   │
   ▼
[WhoisChecker] (Priority 30)          ──> TCP 43 端口查询注册状态词？
```

### 权威性与可用性边界
- 只有权威源（RDAP、WHOIS 或独占 API）返回明确的否定标记（如 `no match`, `not found`）时，系统才会置 `registration_record_absent = true`。
- **DNS 查询未命中、TLD 不支持或解析超时一律保持未知（Inconclusive）**，绝不假定域名未注册。
- `registration_record_absent` **不等于商业可购**（仍需考虑注册局保留词、溢价定价及注册商配额）。

### 熔断器 (Circuit Breaker)
每个网络检查器均配备独立的 `CircuitBreaker`（`src/checker/circuit_breaker.rs`）：
- 连续失败达到阈值（20 次）触发熔断（Open 状态）。
- 冷却期（30 秒）后进入半开状态（Half-Open），放行单个探测请求。
- 探测成功即自愈恢复，失败则继续保持熔断。

## 四、 后台调度与 Worker 执行模型

### 1. 任务排期与拾取
调度器轮询 `scans` 表中状态为 `pending` 的任务，按 `priority DESC, created_at ASC` 排序。同一时刻由独占 Worker 协程驱动单一任务。

### 2. 候选流式供给 (CandidateFeeder)
为避免在内存中一次性展开数百万候选词，`CandidateFeeder`（`src/web/candidate_feeder.rs`）采用**惰性生成器**模式：
- 将生成的域名持续压入有界异步通道 `async_channel`（容量 1000）。
- 内存消耗恒定，无论扫描目标是 100 个还是 200 万个域名。

### 3. 工作线程池 (Worker Pool)
- 启动 10 个并发协程（`src/worker.rs`）从通道并发消费域名。
- 各 Worker 经由 `CheckerRegistry` 检测后，将结果通过 `mpsc` 发回汇聚主协程。
- 结果以 50 条为一个批次（`batch_size = 50`）批量写入 SQLite `results` 表，并触发 SSE 推送。

## 五、 自适应限流与重试队列机制

为保护公共网络基础设施及防止 IP 被封禁：

1. **DNSHE 全局共享限流**：通过 SQLite 时间戳协作，在跨进程、跨任务间严格控制在 30 次/分钟以内。
2. **WorkerThrottle 自适应降级**：
   - 当检测到 WHOIS 返回限流响应时，全体 Worker 首先暂停 60 秒。
   - 随后将工作协程并发数减 1。
   - 若并发数已降至 1，则每次查询增加 20% 的等待间隔。
3. **有界延期重试队列 (Deferred Retry Queue)**：
   - 超时或被限流的域名不会直接丢弃，而是压入延期重试队列。
   - 冷却完毕后，在后续轮次中与新生成的域名交替执行重试（最多 3 轮）。

## 六、 任务状态机与崩溃恢复设计

### 状态机生命周期
```
           ┌───────────┐
           │  pending  │ ◄───────┐
           └─────┬─────┘         │ resume
                 │               │
                 ▼               │
           ┌───────────┐   pause │
           │  running  ├─────────┴─┐
           └─────┬─────┘           │
                 │                 ▼
                 │           ┌───────────┐
                 │           │  paused   │
                 │           └───────────┘
                 ├─────────────┐
                 │ cancel      │ finish
                 ▼             ▼
           ┌───────────┐ ┌───────────┐
           │ cancelled │ │ finished  │
           └───────────┘ └───────────┘
```

### 崩溃与重启恢复 (`src/web/recovery.rs`)
当服务器异常中断或重启后：
1. 处于中间过渡状态（`cancelling` / `pausing`）的任务直接归一化为最终状态。
2. 扫描计数器依据 `results` 表中的真实持久化行数进行原子校准，纠正可能由于断电未提交的内存计数偏差。
3. 中断的 `running` 任务自动置回 `pending`，由调度器重新分配执行，跳过已持久化结果的域名。

## 七、 持久化与数据库架构

SQLite 开启 WAL 模式及外键级联删除约束：
- **`scans`**：任务主表（ID、状态、规则类型、总数、进度计数、优先级、创建/完成时间）。
- **`scan_payloads`**：任务的静态输入载荷（组合字典 ID 列表、前缀、后缀、正则表达式）。
- **`results`**：扫描结果明细（`scan_id`、`domain`、权威无记录标志、到期日、检测来源签名）。
- **`scan_logs`**：实时流式日志记录。
- **`dictionaries` / `dictionary_words`**：持久化词库与词条。
- **`published_scans` / `published_domains`**：公开发布集合及其跨任务搜索索引。
